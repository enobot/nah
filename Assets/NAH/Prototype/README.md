# NAH Unity movement / combat / interaction prototypes

Copied from the owner's `NAH_Research_Code.zip` on 2026-10-31. They had not been compiled there. This repository has not play-tested them yet.

These five C# files are **original example code**, not copied from a third-party repository. They are written for a Unity 6 project with Unity's **Input System**, but **have not been compiled or executed in a Unity Editor** here. They are **LOCAL/OFFLINE PROTOTYPES**, not secure online multiplayer implementations.

## Setup (prototype)
1. Inspect the existing `enobot/nah` repo, Unity Editor version, Input System version, and current architecture. Do **not** overwrite existing scripts.
2. Create an Input Actions asset with an action map for `Move` (Vector2), `Look` (Vector2), `Jump`, `Sprint`, `Attack`, and `Interact` (Buttons). Bind desired keyboard/mouse/gamepad inputs. Add PlayerInput to the player prefab and assign the asset.
3. Put CharacterController and `NAHLocalMotor` on player root; add a child Camera Pivot Transform containing Camera; assign pivot. Assign this Camera to NAHLocalInteractor.
4. Add `NAHLocalHealth`, `NAHLocalMelee`, and `NAHLocalInteractor` to player root. Set Melee Attack Origin child transform, hittableLayers, and environmentOccluders. Give each target colliders (on relevant layers) and `NAHLocalHealth`.
5. Add `NAHLocalHealPickup` and a Collider to any placeholder pickup; ensure interactionMask includes its layer.
6. Test in a throwaway scene. Do not use these scripts in an online session as-is.

## Important caveats
- Health, damage, items, movement, and hit results are LOCAL ONLY. Online PvP needs server-authoritative validation, anti-cheat, lag compensation, state replication, match flow, and reconciliation.
- Current attack is an instantaneous overlap sphere, **not** a finished Soulcalibur-like combo, hitbox timeline, cancel window, shield, critical hit, or animation system. Replace it with a state-driven ability and animation system after approving combat feel.
- Input setup and camera enable/disable must be adjusted for multiplayer per-player ownership. Controller action delta and mouse look sensitivity must be tuned/approved.
- For local split-screen, configure PlayerInputManager, camera association, input pairing, and separate UI per player.
- `GetComponentsInParent` interaction lookup allocates when interaction is pressed; profile if used frequently.
- `OverlapSphereNonAlloc` uses a fixed-size buffer, so it may truncate results. Account for that when building production collision queries.
- Camera clips through geometry and look pitch/gamepad acceleration are not yet tuned. Ground snapping, moving platforms, sliding, climbing, dashing, dodging, knockback, and flying are not included.
- `NAHLocalMotor` should not coexist on the same root with a dynamic Rigidbody-driven motor. Pick the movement/physics integration deliberately.
- No character designs, motion personalities, arena colors, or character rigs are finalized here. Creative approval is required.

## Two-player network arena (gray placeholder)

These files are project code written for this repository. They use Netcode for GameObjects 2.13.3 with direct UDP. There is no Relay, Lobby, or voice chat.

| File | What it does |
| --- | --- |
| `NAHNetworkPlayer.cs` | One fighter. The owner sends input once per network tick (30 a second), and at once when Block or Sprint changes, when it starts or stops moving, and on a jump or attack press. The host moves the body, checks hits, and changes health, lives, and elimination. A client never chooses the target, the damage, or the position used for a hit. Input with NaN or infinity is dropped. The host computes this fighter's stats and accepts one body choice, only before the fighter has attacked or been hit. The body size is shared, so every screen draws and hits the same capsule. Fighters spawn 10 cm above the floor so a long first frame cannot drop them through it. The character controller's minimum move distance is 0, so a slow body still moves at very high frame rates. Input messages are numbered, and the host ignores one older than the newest it has used. A joining player predicts its own fighter: its screen moves a hidden local capsule with the same movement rules and the input it sent, and the camera rides on that capsule. Each network tick the host sends that player where the fighter really is, with the newest input number it had used and for how long, and the screen corrects only the difference from its prediction for that same moment. Small corrections are spread over 0.1 s; one over 1 m (for example the return to the spawn point when the match starts) is shown at once. While the fighter is down or out, the view follows the networked body until it can move again. On a joining player's screen the other fighters' character controllers stay on as solid obstacles (only the host moves them), so the prediction bumps into another fighter where that screen shows it, instead of passing through. Every screen smooths the other fighters; that setting is the host's, and Netcode copies it to every screen. |
| `NAHMotionHistory.cs` | The joining player's short record of its prediction, used to find the predicted state for the moment the host reports. Plain C#, tested without a network. |
| `NAHPoseHistory.cs` | The first part of the owner's middle-ground hit rule. A record of where a fighter stood and faced over the last second, blended between poses, and `RewindTime`, which limits how far back a swing may be checked: never past the limit, never into the future, and no rewind at all for a broken report. Plain C#. Nothing uses it yet: hits are still decided at current positions. |
| `NAHStatRules.cs` | Body shape (size, fatness, roundness, each 0 to 1), weapon weight and length, and race and class ratios become stats: max health, armor (absorption), shielding, attack damage, move speed, swing time, reach, and hitbox size. A hit removes the attacker's damage less the share the target absorbs. Every number is a placeholder. |
| `NAHWeaponDefinition.cs` | A weapon's category, weight, length, and base damage, as gameplay data. Heavier hits harder and swings slower; longer reaches farther and swings slower. |
| `NAHRaceDefinition.cs`, `NAHClassDefinition.cs` | A race's or class's display name, introduction, and ratios on top of body and weapon. |
| `NAHRoster.cs`, `Roster/` | The races and classes a player can pick, in a fixed order. `Roster/` holds PLACEHOLDER assets: 12 races with plain species names and 8 classes with generated names, using the ratios proposed in `GAME_DESIGN.md`. Rename or retune them in the Inspector; the builder will not overwrite them. |
| `Editor/NahPlaceholderRoster.cs` | Creates the placeholder roster the first time the arena is built. |
| `NAHPlaceholderStatRules.asset`, `NAHPlaceholderWeapon.asset` | The placeholder numbers. Tune them here in the Inspector, not in code. The arena builder creates them once and then leaves them alone. |
| `NAHNetworkMatch.cs` | Host-side roster. The match waits until the host presses Start, which needs at least two players and everyone ready (owner decisions). Start puts everyone back at their spawn point at full health. Nobody can be hurt before Start or after the end. It decides who wins. |
| `NAHNetworkSession.cs` | Placeholder connect screen (Host, Join, address field), Ready and Start buttons, and health/lives text. Not the final UI. Through connection approval the host refuses a fifth player, and anyone once the match has started. A silent connection is dropped after 30 s (owner decision), and a joining player is told why the connection ended. |
| `NAHNetworkLagSimulator.cs` | Development builds only. `--nah-lag delay,jitter,drop` adds delay, jitter, and packet loss to this peer's traffic in both directions, through Unity Transport's simulator stage. A round trip grows by about twice the delay. |
| `NAHNetworkDemoDriver.cs` | Development builds only. With `--nah-demo`, it plays the local fighter through the same input messages as the keyboard and can save frames for a video. It logs input messages per second, how long the fighter's own walk takes to show on its screen (measured at the camera), how many frames a second the own view and the nearest opponent move on screen (a smoothed body moves every frame, an unsmoothed one about 30 times a second), and the joining player's prediction corrections. `--nah-walk-test N` stands still and walks N times before readying up, to measure the walk delay many times. `--nah-capture-fps N` (1 to 60, default 10) sets the frame capture rate. `--nah-push` keeps walking into the opponent instead of holding at swinging range, to measure corrections while two bodies push. Two experiment switches help choose how other fighters are smoothed: `--nah-smoothing type,lerp,seconds` (type `legacy`, `lerp`, or `damp`; lerp `0` or `1`; seconds up to 1, for example `legacy,1,0.1`) changes Netcode's smoothing of the other fighters on that screen only, and `--nah-track file` writes, 100 times a second, the clock, the phase, and where this fighter and the nearest opponent are on that screen. The clock is Windows' performance counter, which every window on one PC reads the same, so two windows' files line up and show how far in the past each screen shows the other fighter; the walk-delay log lines carry the same clock. The log also gives "other stalls", the share of frames the nearest opponent stood still between its first and last move (about 0 % when smoothed, most frames when it moves in 30-a-second steps). Each window readies up a second after it arrives; on the host it presses Start once `--nah-start-players` players (default 2) are in and ready. It is a test tool, not an AI opponent. |
| `Editor/NahNetworkArenaBuilder.cs` | Menu **NAH → Create Network Arena**. Rebuilds `NetworkArena.unity` and `NAHNetworkPlayer.prefab`. |
| `Editor/NahBuild.cs` | Menu **NAH → Build Windows Development Player**. Builds only the network arena. |
| `Editor/NahNetworkRulesTest.cs` | Edit Mode tests: a host hit removes exactly what the stat rules say, the last life ends the match, only the local camera and listener are on, the server ignores non-finite input, a body is chosen once before combat, swings, lock-on, races and classes, and the shield. Network tests: a fifth player is refused, nobody joins once the match has started, the host can start only with two or more players and everyone ready, nobody is hurt before Start, the host approves itself and others, the owner's 30 s timeout is applied, input goes out once per tick, an older input cannot undo a newer one, every fighter is smoothed on the other screens, a predicted walk ends where the host moved the body, corrections are spread out unless they are big, a predicted walk into another fighter stops where the host body stops, controllers are on only where they should be, the prediction record finds the host's moment, and the lag simulator reads its settings and adds the delay it promises. |
| `Editor/NahPoseHistoryTest.cs` | Edit Mode tests for the pose record: blending between poses, facing that turns the short way round, the nearest pose outside the record, dropping old poses, a safety limit, ignoring late and broken poses, a clear after a teleport, the rewind limit, and the owner's 150 ms limit. No network or scene needed. |
| `Editor/NahStatRulesTest.cs` | Edit Mode tests for the stat rules: bigger bodies get more health, armor, shielding, and damage, move slower, and have bigger hitboxes; heavier weapons hit harder and swing slower; longer weapons reach farther and swing slower; race and class act as ratios; broken data and invalid bodies are rejected; an average body keeps the old prototype numbers. |

### Play it by hand on one PC

1. Build with **NAH → Build Windows Development Player** (output: `Builds/Windows-Dev/NAH.exe`, ignored by Git).
2. Start the exe twice. In the first window press **Host**. In the second keep `127.0.0.1` and press **Join**.
3. In both windows press **Ready up**. Then press **Start match** in the host window.
4. Temporary keys: WASD, mouse, Space, Shift, left click, right click to block, and middle click or Q to lock on.

Command-line options: `--nah-role host|client`, `--nah-address <ip>`, `--nah-body size,fatness,roundness` (three numbers from 0 to 1, until a character creator exists), `--nah-race <name or number>` and `--nah-class <name or number>` (from the placeholder roster), and `--nah-listen 127.0.0.1` (same-PC game traffic stays off the network, so Windows does not ask to open the firewall; development builds still announce themselves on the local network for Unity's Profiler). Development builds also accept `--nah-lag delay,jitter,drop` in whole numbers, for example `75,15,3`: 75 ms each way, give or take 15 ms, with 3% of packets lost. On two PCs, the host uses the default listen address and Windows may ask the owner to allow the game through the firewall. That choice belongs to the owner.

### Known limits

- A joining player's own movement is predicted (see `NAHNetworkPlayer.cs` above). Measured on 2026-11-01, 16 walks per window: the walk shows 77 to 85 ms after the input on one PC and 67 to 88 ms with 75 ms of simulated delay each way, about the same as the host's 80 ms. Before, it was 234 to 341 ms on one PC, because Netcode smoothed the client's own fighter.
- On a joining player's screen the prediction bumps into the other fighters where that screen shows them, which is slightly in the past (Netcode's smoothing); the host bumps into where they are now. Before this change the prediction passed through them, and pushing gave corrections of up to 18 cm per half second in a crowded four-player fight. Its tests pass (Baseline 7 in `BASELINE.md`), but they run only on the host; the corrections on a joining player's screen since the change have not been measured.
- No lag compensation: other fighters are shown slightly in the past, and the host decides hits at its own current positions. The pose record for the owner's middle-ground rule exists (`NAHPoseHistory.cs`), with the owner's 150 ms rewind limit, but is not used yet.
- If the host crashes, a client shows a frozen match for about 30 seconds before it notices (owner decision).
- The disconnect message shows Netcode's raw text. Placeholder screen.
- There is no way to play again after a match ends; restart both windows. A match cannot be cancelled once started.
- Block (right click or left bumper; temporary keys) puts the shield in front. The shield takes front hits until its amount (the Shielding stat) runs out, then it breaks and cools down for 3 seconds before coming back full. A damaged but unbroken shield refills slowly. A blocking fighter cannot swing. All of these numbers are placeholders.
- A swing is a box in front of the body, from feet to head, as long as the weapon's reach (fighting-game style, owner decision). Looking up or down does not change a hit.
- Lock-on (middle click or Q, right-stick click on a gamepad; temporary keys) turns only the local camera toward the opponent nearest the center of view. A quick sideways flick of the mouse or stick switches to the next opponent on that side. The flick itself was not tested with real input devices.
- There are no animations yet, so "heavy weapons look slow" is only a slower swing timer for now.
- No bows, spells, or abilities yet. Races and classes change only stats; there is no character screen to pick them, only command-line options.
